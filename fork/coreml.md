# AI models on the Neural Engine (Core ML)

List: Learn My Edits' image model runs through Apple's Core ML on the Neural Engine, about 3–5× faster than candle on the GPU, once its Core ML file is downloaded (asked first, 43 MB); candle stays the fallback, and Settings ▸ Performance ▸ AI Models picks Automatic, Core ML or Candle (issue #105); the people-parts SegFormer face and clothes parsers and the face mesh run through Core ML on the GPU too, about 5–8× faster per photo, and so do the BiSeNet set's clothes parser (SegFormer-B2, 7× faster) and Sapiens2 (issue #216; converted locally, not published); BiRefNet (Subject and Background masks) and BiRefNet Matting (the hair edge) run on the GPU through Core ML too, about 3–4× faster per mask (issue #264; converted locally, not published); SAM 3 (Object and Describe masks) runs its six parts on the GPU through Core ML in float32, with candle's masks, a click in 9 ms and a prompt in 0.13–0.23 s instead of 0.05–1.5 s and 0.7–2.8 s, at 3.9 GB of memory instead of 17 GB (issue #268; converted locally, never published: SAM 3's licence is not on the allowlist); LaMa (Remove, heal spots, Repair Glare, Wrinkles) runs on the Neural Engine, 2–4× faster per fill (issue #268; converted locally, not published). Branches `perf/105-coreml`, `perf/coreml-parsing`, `perf/216-coreml-parsing`, `perf/264-birefnet-coreml`, `perf/268-sam3-coreml`, `perf/268-lama-coreml`.

## What it does

- **`crates/coreml`** (`lightcraft-coreml`, layer 0): Core ML through objc2, like `crates/macraw` reaches Core Image. `load_package` compiles an `.mlpackage` into a `.mlmodelc` next to it, keyed by the package's `Manifest.json` and the path, size and time of each of its files (`<name>.mlmodelc.key`: a new model, or a model or weights file replaced inside the package, compiles again), and compiles again once when a cached copy no longer loads; `Model::load` (compute units: all, CPU + Neural Engine, CPU + GPU, CPU) and `Model::predict` run `f32` tensors; `Model::predict_many` (issue #268) passes several named `f32` and `i32` tensors and reads several outputs, names, shapes and duplicates checked before Core ML is called. All `unsafe` is in `src/macos.rs`, with `// SAFETY:` on every block; every failure is an `Error`, never a panic; off the Mac a stub returns "unavailable". No Objective-C exceptions are caught (pure Rust), so every selector is checked first and every nil handled (its README lists the calls).
- **People parts: SegFormer-B0 (faces) and SegFormer-B3 (clothes)** (`crates/parsing/src/coreml.rs`, `tools/convert-coreml-parsing.py`), used by the SegFormer and Sapiens2 sets. The converter writes the same networks again in PyTorch from the published tensor names (it matches Hugging Face's `SegformerForSemanticSegmentation` to 4 decimals) and converts them to fp16 ML programs with fp16 outputs; packages go in `<models>/<folder>/coreml/<folder>.mlpackage` in the shared models folder, compiled once by the app beside them. The face parser takes 1 to 8 crops of 512² per call and gives the ten face groups of `face.rs` at 512² (resize, softmax and group sums inside). The clothes parser's input size changes with the photo (long side 768 to 1536), so it takes the photo's grid in the top-left of one of 28 canvases (each long side 768, 1024, 1280, 1536; short sides 1, ¾, ⅔ and ½ of it; both ways round) with a fourth channel marking the photo, and every layer ignores the padding: convolutions see zeros past the photo, attention gives the padding's keys −10⁴, and the decoder's resizes divide the resized masked map by the resized mask (the edge clamp of a resize of the photo alone). In float32 the canvas run equals the run alone to 1.2·10⁻⁶. Both run on the **GPU** (`CpuAndGpu`): the Neural Engine compiler ran over 15 minutes on one 1536 × 1024 clothes canvas without finishing (its first attention is 98,304 × 1,536), and for the face parser the GPU is as fast (11 against 12 ms a face) and about ten times closer to float32 (a made-up crop's person mask moved 0.4–1.4 % on the Neural Engine, 0.03–0.09 % on the GPU). Runtime rows: `face-parsing-segformer-b0` ("People Parts: Faces"), `human-parsing-segformer-b3` ("People Parts: Bodies") and `facemesh-v2` ("People Parts: Face Mesh"); `PeopleParsing::set_runtime` drops the loaded set and never waits for one loading (the set loads without the loaded-set lock held; a set loaded while the choice changed serves its run and is not kept). BiSeNet's face parser stays on candle; SegFormer-B2 and Sapiens2: the next two bullets.
- **The BiSeNet set's clothes parser, SegFormer-B2** (issue #216): the same network as B3 with fewer blocks per stage, converted by the same script (`--model segformer-b2`) to the same canvases and the same square-canvas rule, on the GPU (`human-parsing-segformer-b2/coreml/human-parsing-segformer-b2.mlpackage`, 54.7 MB of weights). Runtime row `human-parsing-segformer-b2` ("People Parts: Bodies (BiSeNet Set)").
- **Sapiens2** (issue #216, `crates/parsing/src/coreml/sapiens.rs`, `tools/convert-coreml-sapiens2.py`): Sapiens2 runs on a box around each person (`crops.rs`), each of another size, and Core ML plans a model again on every new input shape (#200; for this backbone 1.7 s). So the network is cut in two models of fixed shapes, and one call holds several people's passes:
  - the **backbone** (the transformer) takes rows of tokens: each pass's class and storage tokens, then its patches (16 × 16 × 3 pixels each) with the rotary table's sin and cos for the patch (computed in Rust as candle does, bf16 rounding included; 0 and 1 for the class and storage tokens, which are not turned), and the pass's number. A token attends only to tokens of its own pass (another pass's keys get −10⁴), so each pass gives what it gives alone. One package with two functions sharing one weights file (`MLModelConfiguration.functionName`, macOS 15 or later; `lightcraft_coreml::load_package_function`): 1664 rows (a whole photo's pass alone, about 1536 patches) and 3264 (the largest pass `crops.rs` makes, 3225 patches, with its prefix). Both loaded cost 128 MB more than one, not another 800 MB, and switching between them plans nothing again: 345–397 ms against 789–845 ms a call on the GPU. Float16; its norms divide by the largest value first, so the squares never pass float16's range.
  - the **head** (four transposed convolutions, instance norms, the classifier) takes the passes' features on a canvas of patches, each pass in its own rectangle (rows of passes side by side) with an empty patch between two of them and a channel marking it: every layer sees zeros past a pass's edge and every instance norm takes each pass's own mean and variance, so each pass's part of the canvas equals the head on that pass alone. Two packages, 48 × 48 patches (a whole photo's pass of 3:2 either way round) and 96 × 64 (tall boxes); a call takes the smaller that holds its passes. Float32 on the GPU (float16 was no faster; the norms sum over up to 1.5 M pixels).
  - Rust packs the passes into calls (`calls`: at most 9 passes, 3264 rows and the large canvas each), cuts each pass's logits out of the head's output and brings them down to the body map's grid with candle's own resize and softmax on the CPU. A pass larger than the large canvas (a panorama's whole-photo pass, wider than 64 patches) is made smaller in its own shape (`fit`); every pass of the CC0 photos below fits as it is.
  - The **Neural Engine** was tried for the backbone and dropped: 1.43 s a call against 0.75 s on the GPU, and 97 % of a made-up picture's pixels the same class as float32 PyTorch against 99.9 % (its float16 norms and attention drift).
  - Each engine makes the passes at its own sizes (`crops::Runner` takes a maker): when Core ML fails on a photo, candle runs that photo's passes at candle's sizes, never the shrunk ones. A parse is filed under its Sapiens2 engine: the version gets `+coreml` on Core ML (`PeopleParsing::version_of`, so the cache key, the parse-ahead index and the face store), and the cache key `-fit` when the whole-photo pass is shrunk (`Choice::key_version`, `lightcraft_parsing::coreml::sapiens2_shrinks`); candle's key is the one parses had before. On macOS 14 the backbone's function load is refused before anything is compiled (`lightcraft_coreml::functions_available`), so it falls back to candle without compiling on every launch.
  - Runtime row `body-parsing-sapiens2-0.4b` ("People Parts: Sapiens2"); candle stays the fallback (Automatic: candle when the three packages are not all there or don't load, and for good once Core ML fails on a photo). Peak memory of a Sapiens2 parse: 5.2 GB on Core ML against 11.8 GB on candle (a portrait and a street scene, `/usr/bin/time -l`).
- **People parts: the face mesh** (MediaPipe face landmarks v2, every set's; `tools/convert-coreml-facemesh.py`): the safetensors file stores the network as a program of layers in its header, and the converter runs that program in PyTorch as `facemesh.rs` runs it on candle. Up to 8 crops of 256² a call; one output `mesh` [B, 1435] per crop: the 478 points (x, y, z in crop pixels), then the face score before its sigmoid (one output, so `crates/coreml` reads one tensor per call). **Float32 on the GPU**: for this small network as fast as float16 (about 10 ms for 8 crops) and equal to PyTorch's float32 to 0.0005 px, where float16 moved points by up to 0.5 px and the Neural Engine by 3.5 px (and was slower, 35 ms for 4 crops). Package `<models>/facemesh-v2/coreml/facemesh-v2.mlpackage` (4.8 MB of weights).
- **BiRefNet and BiRefNet Matting** (issue #264, `crates/birefnet/src/coreml.rs`, `tools/convert-coreml-birefnet.py`): the converter runs BiRefNet's own PyTorch code (`birefnet.py` of the Hugging Face repo, MIT, given with `--code`; not part of LightCraft) on the weights in each model's folder, with torchvision's deformable convolution written as `grid_sample` sums (Core ML has none), and converts the network to a float16 ML program at the one input candle uses for both, 1024² (`pixels` [1, 3, 1024, 1024] in, `logits` [1, 1, 1024, 1024] out, before the sigmoid, as candle's `Matte`). Packages `<models>/birefnet/coreml/birefnet.mlpackage` and `<models>/birefnet-matting/coreml/birefnet-matting.mlpackage`, 450 MB each, on the **GPU** (`CpuAndGpu`; the Neural Engine took 11 s a run and over 4 minutes to load, #115). `BiRefNet::load_with` takes the runtime: Automatic is Core ML when the package is there and loads, else candle on Metal; a Core ML run that fails hands that run and every later one to candle; the CPU fallback after a GPU failure is candle's. Runtime rows `birefnet` ("Subject Masks: BiRefNet": read when a Subject or Background job is queued) and `birefnet-matting` ("Hair Edges: BiRefNet Matting": `HairEdges::set_runtime`). The matte cache and the people-parse cache do not say the engine: the two mattes agree to 10⁻⁴ (below).
- **LaMa** (issue #268, `crates/lama/src/coreml.rs`, `crates/engine/src/lama_fill/coreml.rs`, `tools/convert-coreml-lama.py`): the converter writes big-lama's generator again in PyTorch from the candle port (it matches the TorchScript original to 3·10⁻⁶; coremltools lowers its `rfftn` / `irfftn` to matrix products that run whole on the Neural Engine) and converts it to a float16 ML program with one function per square side, 128, 256, 384, 512 and 768, sharing one weights file (`<models>/lama/coreml/lama.mlpackage`, 103 MB; macOS 15 or later). LaMa's crops change size with every spot, and Core ML plans a model again on every new shape, so a crop is mirrored at its right and bottom up to the smallest side that holds it (candle mirrors it up to a multiple of 8 the same way) and the fill is cut back. The Remove panel's crops are at most 512 on a side, Wrinkles' at most 768, a heal spot's about 100 to 250. On the **Neural Engine** (`CpuAndNeuralEngine`; GPU 0.3 s and All 0.3 s a 512 fill in the trial): 6, 22, 50, 95 and 230 ms a fill against 40–160, 70–170, 150–240, 200–460 and 700–960 ms on candle (Metal). On Automatic, crops under 96 px stay on candle (20–80 ms there, and mirroring them to 128 more than doubles them). Its first load on a Mac plans each function for the Neural Engine, about a minute for the five; later loads take a few seconds. So the engine loads it on a thread of its own, as background preparation (the top bar's ring, "Preparing LaMa for the Neural Engine"), at its first need: the first fill, or a tool that fills being shown (the Remove panel with the LaMa fill, Repair Glare's LaMa method, Wrinkles; `LamaFill::prepare`), never at launch. Every fill until it is ready runs on candle; one load at a time, even when the runtime changes while one runs. The loaded model is kept, not released after a minute like candle's: it holds 53 MB of the process after loading and 104 MB after a fill at every side (130 MB at its peak; candle's is 2.8 GB), dropping it gave none of that back, and a reload takes 2–3 s, or a minute when macOS has dropped its Neural Engine plan, during which fills would go to candle. A Core ML fill takes no GPU turn (`gpu_run`), so a fill waiting on the first load never holds up the GPU models. A Core ML fill that fails, or gives a fill of the wrong size or with a number that is not finite, hands that fill and every later one to candle on Automatic and is the fill's error on Core ML. `LamaFill::set_coreml_units` loads it again on other units (#267). Runtime row `lama` ("Remove and Heal: LaMa"). The fills cache does not say the engine: a fill kept from candle is given again after Core ML is ready.
- **SAM 3** (issue #268, `crates/segment/src/coreml.rs`, `tools/convert-coreml-sam3.py`): the converter splits Hugging Face transformers' PyTorch SAM 3 (Apache-2.0) into six float32 ML programs at the steps candle's port runs: `encoder` (pixels → backbone, once per photo), `clickfeat` (the click decoder's features, once per photo), `clickdec` (per click), `textfeat` (the prompt features, at the first prompt on a photo), `textscore` (the 200 queries' scores, per prompt) and `textmask` (their masks and the semantic mask, only for a prompt that matches: candle skips its pixel decoder then too). Packages `<models>/sam3-coreml/sam3-<part>.mlpackage`, a sibling of the `sam3` folder, which is never written to; on the **GPU** (`CpuAndGpu`; the Neural Engine never compiled the encoder). Clicks go in 65 fixed slots (the app's 64 and the "not a point" that closes the list): unused slots are masked out of the two attentions that read the click tokens, every other step works on each token alone, so the masks are those of the clicks alone; padding with "not a point" tokens instead broke masks (IoU down to 0.0), and one shape per click count would plan the GPU again for each count. Each output is checked for its size and for numbers that are not finite. `Sam3::load_with` takes the runtime (and `load_with_units` the units, for #267): Automatic is Core ML when all six packages are there and the encoder and click parts load, else candle on Metal; a part that fails hands that run and every later one to candle, which makes its backbone from Core ML's numbers; the CPU fallback after a GPU failure is candle's. Both engines' decoder outputs go through the same mask choice (`tracker::Heads`) and prompt merge (`detector::merge_with`). Core ML plans each part on the GPU at its first run after a load (1.6–5.6 s), so the parts the user has not run yet are run once on made-up inputs while the worker is idle (`crates/engine/src/segment/worker/warm.rs`), click decoder first: only after a reply has gone out and no request waits, one warm-up at a time, in the top bar's ring ("Getting AI masks ready", started by the app). `Worker::submit` pauses it: it stops between parts, so a request waits at most for the one part being planned, never for a part the user is running (`WarmUp::step` skips it) and never for the parts left; the next idle moment resumes them. Stopping it from the ring, or a part that fails, ends it for the loaded model. The remote worker (`lightcraft-sam3-worker`) loads Automatic too and warms up the same way between requests. Runtime row `sam3` ("Object and Describe Masks: SAM 3": read when a job is queued; a change loads the model again).
- **One input shape per model** (issue #200): Core ML plans a model on the GPU again whenever the input shape differs from the call before, and keeps only the last plan: for the clothes parser about 300 ms of wall and CPU time, more than four runs (68 ms, 28 ms CPU, in one shape; `crates/parsing/examples/coreml_shapes.rs`); `MLModelConfiguration`'s reshape hint is already "frequent" by default, and a second loaded copy per shape avoids it but holds 300–500 MB more. So the clothes parser always takes the square canvas of its grid's long side (`coreml::canvas`: 768² for every photo but small-faced groups; the converted package lists the squares, so nothing is converted again), about 40 ms more wall time on the GPU and the same CPU time; the face parser takes full batches of 8 in one call and any other number one crop a call (a group of 26 then a portrait: 376 ms, 233 ms CPU, against 442 and 286 ms as 8, 8, 8, 2 then 1); the face mesh always takes 8 crops, the unused ones blank (0.8 ms a face against 9 ms one at a time). A call in the new shape gives what the old shape gave (a test on made-up pixels: 99.9 % of pixels the same class, mean difference under 0.002); masks on 14 CC0 photos in `fork/parse-ahead.md`.
- **The first model: DINOv2-small**, Learn My Edits' image encoder. It is merged, small (88 MB) and a plain ViT, the kind the Neural Engine runs best, so it is the cheapest proof. The people-parsing SegFormer (PR #92), BiRefNet, LaMa, the face models and SAM 3 are follow-ups.
- **Conversion, once, by hand** (`tools/convert-coreml-dinov2.py`, versions in `tools/requirements-coreml-convert.txt`): the same network written again in PyTorch from the published tensor names, with candle's exact 224 × 224 input and 37 × 37 → 16 × 16 position resample, converted to an fp16 ML program. It reads the `model.safetensors` already in `~/Library/Application Support/ArtCraft/models/dinov2-small/` (never a second download) and can install `coreml/dinov2-small.mlpackage` next to it (43 MB). The app compiles it there once, into `coreml/dinov2-small.mlmodelc` (about 2 s, at the first job).
- **Download** (`crates/engine/src/model_runtime/download.rs`): converted files of small models (under 2 GB) whose licence allows redistribution are published once, zipped (stored), on the `models-coreml-1` release of techneissa/lightcraft. Settings ▸ Performance ▸ AI Models shows "Download Core ML Model (43 MB)…" on a Mac without it, asks "Download the Core ML model (43 MB) from github.com?", and downloads with a row in the activity stack (`models.downloadCoreml {model, confirm: true}` for agents; refused without `confirm`). The zip's size and SHA-256 are checked like LaMa's, it is unpacked into the model's `coreml/` folder in the shared models folder (an entry outside the package, a link, too many files or bytes: nothing is installed) and deleted. Without the release the download fails with a message and the model stays on candle; the app never converts anything.
- **Runtime per model** (`crates/engine/src/model_runtime.rs`, kept in `<config>/model-runtimes.json`): Automatic (default: Core ML when its model is there and loads, else candle; candle also takes over for good when Core ML fails on a photo), Core ML (an error when it can't run), Candle. Settings ▸ Performance ▸ AI Models has one row per model; `models.runtime {model, runtime}` sets it, `models.runtime {}` lists it with `coremlAvailable`, `coremlInstalled` and the `backend` in use; `learn.status` carries `runtime`, `coremlInstalled`, `backend`.
- **Fastest unit per model** (issue #267, `crates/engine/src/model_units.rs` and `model_units/`): on Automatic (and Core ML), each model with a Core ML version is measured once per Mac on each unit it can use (Core ML on the GPU, on all units, on the Neural Engine; candle on the GPU for DINOv2 and the two BiRefNets, whose candle ports take Core ML's input), in the background with a row in the activity ring ("Finding the fastest unit for …"), waiting before each option and each run while the photo on screen is being made or a job waits on a model (parses, masks, hair edges, Learn My Edits count themselves), and taking the GPU turn for each run. Each option loads (capped at 90 s: a load over it is left behind, counted until it returns, and remembered; the other Neural Engine option is then not loaded), runs once to warm, then is timed (a run that does not end in 10 minutes fails; time spent waiting for the app does not count) (the mean of up to ten runs when runs are short) on a made-up input of the model's one input shape (`lightcraft_coreml::Sample`). Neural Engine options (all units, Neural Engine) are measured last and one compile at a time: none loads while a load left behind is still going (a model whose unit of old is one of them, Learn My Edits', waits whole, as nothing can be compared without it), and a package of 150 MB or more (the clothes parsers, Sapiens2, the BiRefNets) has them measured only when the app has been idle (parse-ahead's full pace) for a minute on mains power, outside Low Power Mode; until then the model uses what was measured, and the worker takes other models and comes back. Each option is filed as it finishes, with a `complete` flag, so a quit or cancel loses at most the option under way and the next measurement goes on from there (running only the reference again, for its output). The model's unit of old is the reference (its tests hold it equal to candle); another option counts only when its output is within the model's tolerance of it (`model_units/probes.rs` lists them). The measurement is filed under the model files' key (the package's cache key, plus candle's weights file size and time), the input shape, the macOS build and the chip, in `<models>/model-units.json`; a load tries the matching options fastest first, then the unit of old (unless it went over the load cap: with no Core ML unit left, the model loads on candle, Core ML chosen in Settings included), then candle on the GPU, then candle on the CPU (`lightcraft_coreml::first_that_loads`, `UnitOrder`; `BiRefNet::load_in_order`, `Parser::load_with_units`, `ImageEncoder::load_on_units`, `Mesher::load_on_units`). Until a model is measured it loads as before. Settings ▸ Performance ▸ AI Models shows the chosen unit and its time under each model, with Measure Again (`models.measure {model}`; `models.runtime {}` carries `units`). `cargo run -p lightcraft-engine --features sam --example model_units` prints the table below. Two loads of one package (the app's and a measurement's) compile its `.mlmodelc` one at a time (`cache.rs`, a lock per package). Not done: taking a second-best unit while another model holds the best one (a model is loaded once on one unit; that needs a second loaded copy, not a busy count). Known: a Core ML run that fails on a photo hands the model to candle for the session, not to the next unit.

Two candle 0.9.2 faults found on the way:
- On **Metal**, a batch of SegFormer-B0 face crops gives every crop after the first other numbers than the same crop alone (person share of a made-up crop: 0.327 in a batch of 3 against 0.339 alone; another 0.711 against 0.630; one group's value moved by up to 0.93; alone equals PyTorch). Not found in one layer: convolutions (grouped too), matmuls, attention, layer norm, softmax, GELU and resizes each give a batch's items what they give alone. **Handled:** candle's face parser takes one face a call on the GPU on every path (`parser::candle_face_calls`), also when Core ML fails mid-photo and hands it 8 crops; masks over speed (techneissa's call). The face mesh is not hit (a check in `tests/models.rs`) and keeps its batches.
- On the **CPU**, candle's general convolution takes a contiguous input whose strides equal channels-last ones as channels-last: a contiguous NCHW input of one group with as many channels as rows and columns (the face parser's stage-2 reduction, 4 × 4 stride 4 on 64 channels at 64 × 64) is read wrong (largest difference 6.0 on a test input). **Fixed:** `nn::Conv` runs such a convolution with rows and columns swapped in the input, kernel and result (the swapped input is not contiguous, so candle reads it by its strides); candle's CPU face parse now equals its GPU one.
